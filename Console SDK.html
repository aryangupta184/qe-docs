Section 1

What problem we are solving

Everyone on the desk talks to the Console backend, and almost everyone does it by hand. That hand-written access is the problem.

Everyone writes custom clients

Every quant, dev, and ops script re-implements the same plumbing: build the URL, attach auth, set content type, send, parse. The same 10–15 lines are copy-pasted across scripts, each subtly different.

…in multiple languages

The desk is polyglot: strategy/tooling in C++, research in Python, dashboards in TypeScript. Each language re-derives the same plumbing independently.

Manual envelope handling

The backend wraps every response as {success, data, errors}. Miss the check and {"success": false} can be silently treated as success.

AI agents call raw HTTP

Vibe-coding assistants guess URLs, auth, body envelopes, pagination, and retries. The classic failure mode is a confidently retried POST.

No traceability

Calls look like anonymous requests/curl hits. “Which client, version, box, and mode?” is unanswerable.

Dangerous retries

A flaky 503 is often handled with no retry, or a naive retry that re-sends POST /place_order and can double a position.

{ "success": true,  "data": <payload> }
{ "success": false, "errors": <message> }

Section 2

Features and usages

SDK_Final generates one correct, typed, self-identifying client per language, per backend page, straight from the backend’s own API contract.

Auto-generated help text: full ephemeral-DB pipeline

Every SDK ships a <PAGE>_SDK_MIGRATION.md with generation, installation, launch instructions, runnable examples, endpoint docs, parameter tables, and method-level docstrings. It is not hand-written: drf-spectacular runs against a throwaway SQLite DB, emits openapi.yaml, and the docs are rendered from that same spec.

Vibe-coding support

  • Agents call sdk.<resource>.<method>(...), never raw HTTP.
  • Auth, body envelopes, unwraps, and retry policy are handled by the SDK.
  • “Pull today’s holidays and place a hedge” becomes a few method calls instead of fragile request code.

One contract → three typed clients

A single openapi.yaml drives Python typed models, TypeScript schema.d.ts, and C++ nlohmann::json. All three share one response contract and retry policy.

Safe retries: idempotent-only, with tests that prove it

AspectPolicy
Retried methodsIdempotent only: GET, HEAD, PUT, DELETE; never POST/PATCH.
Retried conditionsTransport errors and HTTP 408, 425, 429, 503.
BackoffFull-jitter exponential: random(0, min(cap, base × 2^attempt)).
Retry-AfterHonored for integer seconds or HTTP-date.
Stop conditionsThree retries, four total tries, and a 30-second elapsed budget.

Retry decision tree

flowchart TB

    B -- "yes" --> D{"idempotent method?<br/>GET / HEAD / PUT / DELETE"}
    D -- "no — POST / PATCH" --> E["never retry → raise"]
    D -- "yes" --> F{"attempts < 3 AND<br/>elapsed + sleep < 30s?"}
    F -- "no" --> G["stop → return last / raise"]
    F -- "yes" --> H["sleep max(Retry-After, full-jitter backoff)"]
    H --> A

Versioning pipeline and standalone SDKs

Each page is versioned as an integer and bumped automatically when its API contract changes. SDK generation is standalone: Django is used only to dump the spec against a throwaway DB, generated clients depend only on their target runtime plus HTTP/fetch/json dependencies, and backend changes preserve old routes via advisory headers.

Section 3

Demo

Scenario: onboard a new exchange holiday. The demo exercises Python list → create → update, then proves the same backend is reachable from a latency-sensitive C++ smoke test. Two endpoints each, GET and POST.

Demo flow at a glance

sequenceDiagram
    participant You
    participant SDK as sdk (python / c++)
    participant Backend as Console backend

    You->>SDK: calendar_holiday.list()
    SDK->>Backend: GET /calendar_holiday/ (Bearer + X-QE-SDK-*)
    Backend-->>SDK: {success, data}
    SDK-->>You: data (unwrapped)

    You->>SDK: calendar_holiday.create(created_by, date, reason)
    SDK->>Backend: POST /calendar_holiday/ {"post": fields}
    Backend-->>SDK: {success, data}
    SDK-->>You: created row

    You->>SDK: calendar_holiday.update(id, reason)
    SDK->>Backend: PATCH /calendar_holiday/{id}/ {"patch": fields}
    Backend-->>SDK: {success, data}
    SDK-->>You: updated row

Working internals

The pipeline lives in a modular sdkgen package behind a thin generate_sdk.py entry point.

CLI entry point

generate_sdk.py re-exports sdkgen.cli.main. The CLI takes --page, --languages, optional --skip-spec, and per-page --namespace/--module. Failures are isolated per page, so one broken page cannot stop the other pages from shipping.

Why openapi.yaml?

  1. It is the thing clients are emitted from: one contract, three languages, guaranteed consistent.
  2. It is the thing diffed to detect changes for versioning.

DRF-spectacular + custom schemas on a throwaway DB

spec.py writes ephemeral settings, disables migrations, registers the API URLs, runs Django commands against SQLite, and dumps openapi.yaml. That spec is then parsed into resources and operations.

Template and client generation

Templating is dependency-free. Python packages use openapi-python-client plus a wrapper; TypeScript emits package.json, tsconfig.json, and schema types; C++ emits a CMake project with nlohmann::json.

Auth, unwrap, retries, and headers

All four are generated into every runtime: env-driven auth, startup identity detection, shared retrying HTTP clients, and an unwrap layer that returns data or raises loudly on success: false / errors.

Runtime call layers

sequenceDiagram
    participant R as resource method
    participant Retry as RetryingClient
    participant HTTP as shared httpx client
    participant B as backend

Section 5

Versioning

The manifest is the source of truth

{
  "pages": {
    "holiday":  { "version": 1, "languages": ["python", "typescript", "cpp"] },
    "automate": { "version": 1, "languages": ["python", "typescript", "cpp"] }
  }
}

sdk_manifest.json drives both all-page generation and the versioner. Onboarding a page is one line at version: 1.

Full pipeline: fetch artifacts, as CI runs in CI today

Versioning pipeline

flowchart TB
    edit["Dev edits a serializer / endpoint"] --> push["git push (any branch)"]
    push --> ci["CI `sdk` job"]
    ci --> fetch["git fetch origin $CI_DEFAULT_BRANCH<br/>(read-only baseline)"]
    fetch --> regen["regenerate openapi.yaml from CURRENT code"]
    regen --> diff{"spec differs from<br/>default branch?"}
    diff -- "no (pure refactor)" --> nobump["no bump"]
    diff -- "yes (real change)" --> bump["version = default-branch + 1"]
    bump --> sdk["regenerate full SDK (py/ts/cpp) at vN<br/>+ # vN CHANGELOG.md"]
    sdk --> publish["publish generated/ + manifest as CI artifacts"]

    classDef box fill:#26292d,stroke:#3a3f44,color:#f2f4f8;
    classDef decision fill:#2e3338,stroke:#3a3f44,color:#f2f4f8;
    class edit,push,ci,fetch,regen,nobump,bump,sdk,publish box;
    class diff decision;
  • Baseline is read via git show/fetch, not by mutating the repo.
  • State is detected by parsed-YAML equality against the baseline spec.
  • Only real API changes bump; pure refactors do not.
  • Broken pages are skipped unless strict mode is requested.
  • CI uploads generated SDKs and manifests as artifacts; no commits, pushes, or protected-branch access are needed.

Why “stable vs beta” channels do not work here

Versioning is per-page and baseline-relative. There is no single global release line where “stable vs beta” makes sense. Branch artifacts are ephemeral, and a persistent beta channel adds state without solving the core problem.

Better than commit-back: publish to S3/SG and fetch via API

CI should upload bundles under versioned keys such as sdk/<page>/v<N>/..., then POST the latest version to a small service or Redis. Consumers fetch /sdk/<page>/latest and then download the matching bundle.

Routing versions via SdkContextMiddleware

For compatibility, one backend endpoint must serve multiple live versions. The generated SDK sends X-QE-SDK-Version, and middleware parses it into request.sdk. A dispatch map routes major versions to version-specific handlers; old clients keep working while new clients use new fields/behavior.

Caller headerRouted toWhat it sees
X-QE-SDK-Version: 1v1 legacy handleroriginal response shape
X-QE-SDK-Version: 30v30 handlerv30 contract
X-QE-SDK-Version: 40v40 latest handlernew fields/behavior
def dispatch(request, *args, **kwargs):
    version = request.sdk.version
    handler = VERSION_HANDLERS.get(version, VERSION_HANDLERS[SDK_DEFAULT_VERSION])
    return handler(request, *args, **kwargs)
